00 · AGENT DEVELOPMENT LIFE CYCLE

One human.
One feature.
Six agents that stay in their job.

ADLC is an operating model for building software with AI agents. One engineer owns a feature from requirement to production. Specialist agent personas prepare every stage. The engineer accepts every gate. Tests exist before the feature code. One feature folder carries the context, so no stage depends on chat memory.

01 · WHY

Agents did not create a new process problem. They exposed the old one.

Today

  • A feature waits in a queue between requirement, architecture, design, build, test and release.
  • Context is rebuilt at every hand-off. Nobody holds the whole outcome.
  • Tests are written after the code, by whoever has time.
  • With agents added naively: one long chat, one bloated context, one agent that quietly redesigns the plan to make its own code pass.

ADLC

  • The work still passes every stage. The queue between roles becomes a gate the engineer accepts.
  • Each stage is run by a persona in a fresh context, from the files in the feature folder.
  • Tests exist before the feature code. The build makes them pass; it does not rewrite them.
  • Anything that is 1 + 1 = 2 is a deterministic check, not a paragraph begging the model.
P1

Small tasks, fresh context

Models have a smart zone and a dumb zone. One stage, one session, read the files, stop. Clear rather than compact.

P2

Align before artefact

Stage 1 interviews the human until the requirement is testable. Specs-to-code without alignment is vibe coding with extra steps.

P3

Tests before code

Stage 5 writes failing tests from the requirement and design. Stage 6 makes them pass without touching stage 3.

P4

Vertical slices

The build plan cuts tracer bullets across layers. Every slice is demonstrable, so feedback arrives early and slices can run in parallel.

P5

Deterministic over prose

Gate checks run as code: ids traced, red run recorded, approvals bound to a hash. Prose can be argued with; a failing check cannot.

P6

No defect escapes twice

Every escaped defect becomes one line in a rule, one new check, or one template change. Never a paragraph.

03 · THE SIX AGENTS

Each agent is a persona: a role, a body of knowledge, a set of outputs, and a clear limit.

The same model can play all six. The persona keeps each one inside its job. A defines why and what. B defines where it fits. C defines how it should work. D plans and builds it. E proves it. F coordinates the date and prepares the release — and cannot approve its own change.

04 · THE CONTEXT CARRIER

One feature folder. The next agent reads the files, not the chat.

features/001-rate-limit-login/
├── 01-requirement.md        A · REQ-n, NFR-n, out of scope, interview record
├── 02-system-map.md         B · components, data flow, dependencies
├── 03-solution-design.md    C · modules, interfaces, errors, security, DR-n
├── 04-build-plan.md         D · vertical slices, files, feedback loop
├── 04-build-log.md          D · one line per slice built
├── 05-test-plan/            E · id → test mapping, red run
├── 06-test-summary.md       E · id → result → evidence
├── 07-change-pack/          F · timeline, uat, deploy, rollback, approvals
└── gates.json               ✓ approvals bound to artefact hashes

Why a folder, not a thread

A chat thread is the dumb zone waiting to happen. A folder is a stable starting state: any agent, any model, any day can open it and know exactly where the feature is. It also makes the work reviewable by people who were never in the conversation.

Ids are the thread

REQ-1 is written once in stage 1. It appears in the system map, in a design rule, in a test name, in a result row, and in UAT. adlc check fails any stage that drops one.

Doc rot is handled

When the feature ships, the folder is archived. Agents do not read old PRDs as if they were current truth.

05 · GATES

Agents prepare. Humans accept. Approvals are facts about a file, not memories about a conversation.

Every gate has two halves. Deterministic: adlc check verifies the artefact exists, ids are traced, open questions are empty, the red run is recorded, the rollback was rehearsed. Judgement: the engineer answers the question only a human can — is this the right scope, does it fit, would you ship on this evidence.

When the engineer accepts, adlc approve records the SHA-256 of the artefact. If the artefact changes afterwards, the gate turns stale and must be renewed. Re-approving an early gate drops every approval downstream. Agents never run approve.

    08 · THE SKELETON

    Everything you need is markdown and one script. No framework. No dependencies.

    your-repo/
├── AGENTS.md                 entry point any agent reads first
├── .cursor/
│   ├── rules/
│   │   ├── core.mdc          always-on, under 15 lines
│   │   ├── adlc-flow.mdc     applies inside features/**
│   │   ├── lessons.mdc       one line per promoted lesson
│   │   └── stack.mdc         your stack, your globs
│   ├── skills/
│   │   ├── adlc-new/         create folder + stage-1 interview
│   │   ├── adlc-stage/       run one stage with its persona
│   │   └── adlc-gate/        walk the human through a gate
│   └── agents/
│       ├── adlc-builder.md   D · one slice, TDD, parallel-safe
│       ├── adlc-verifier.md  E · run everything, trace evidence
│       └── adlc-critic.md    read-only review, fresh context
├── adlc/
│   ├── personas/             A–F
│   ├── templates/            01…07
│   ├── gates.md  autonomy.md  lessons.md
├── features/                 one folder per feature
└── scripts/adlc.mjs          new · status · check · approve

    Rules, skills, subagents, personas — which is which

    Rules
    Always-on constraints. Thin. Grow by one line per lesson.
    Skills
    Repeatable procedures: start a feature, run a stage, walk a gate. Loaded only when invoked.
    Subagents
    Separate contexts for noisy or parallel work: build a slice, verify, critique.
    Personas
    The role a stage is run as. A persona is a file the skill or subagent loads; it is not a fourth system.

    Works with

    Cursor (rules, skills, subagents as shipped). Claude Code (CLAUDE.md → AGENTS.md, skills → .claude/skills, agents → .claude/agents). Any agent that can read a folder and run a shell command.

    git clone <repo> adlc && cd adlc && npm test && npm run site
    node scripts/adlc.mjs new my-feature --title "My feature"

    09 · ADOPT

    Start small. Learn. Scale what the evidence showed.

    StageWeeksWhat we doWhat we look for
    Shadow1–2One feature, humans do every stage, agents watch and summarise. Fix the templates.Where context was rebuilt by hand. Which questions stage 1 should have asked.
    Assist3–8Agents draft every artefact. Humans accept every gate. Lessons go to lessons.md weekly.Edit distance between draft and accepted. Defects escaping each gate.
    Act9–16D builds slices in a branch; E writes tests in a branch. Parallel builders on independent slices.Zero escaped defects at G5/G6 across 5 features. Review time per PR.
    Scale17+Run the proven path on many features. Promote personas individually.A deterministic check exists for every defect class seen so far.

    Capacity does not grow because agents exist. It grows because each engineer can hold a whole feature, with evidence ready as the work moves.
